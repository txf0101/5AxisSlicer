# 2026-07-03 项目结构注释复盘

## 本轮目的

本轮把“每个目录、每个文件做什么”整理成集中结构索引。项目虽然代码量不大，但已经包含 GUI、CAD 读取、VTK 渲染、HTTP 自动化、真实模型示例、截图产物和 IDE 配置；若只靠口头说明，后续继续改选择逻辑或自动化测试时容易把输入资产、生成产物和源码边界混在一起。

## 取舍判断

结构说明采用 `docs/project_structure.md` 单文件维护。若把用途说明散落到每个源码文件顶部，重命名、移动、删除文件时会增加同步成本；集中索引更适合当前规模，也方便新对话或新协作者快速建立上下文。

文档没有展开 `.git/` 内部文件。Git 对象库、索引和引用文件由工具维护，人工逐项注释价值很低，反而会诱导误改。对 `outputs/`、`__pycache__/`、`.idea/` 这类可生成或本机相关内容，文档保留用途说明和清理边界，帮助判断哪些文件可以再生成，哪些截图和 JSON 适合临时保留。

## 可复用方法

- 写结构说明前先读 README、复盘和源码入口，避免按文件名猜职责。
- 文件级说明按“运行入口、源码层、脚本层、测试层、示例资产、生成产物、本机配置”拆开，后续新增文件能直接归类。
- 对输出目录采用“文件用途加清理边界”的写法，既保留调试价值，也减少把产物误当源码的概率。
- 对真实模型说明标注依据来源，例如复盘记录、检查报告或文件名推断，避免没有根据的模型结论。

## 沉淀价值

这份结构索引把 CAD 拓扑、VTK 显示对象、Qt 选择状态、HTTP 自动化和项目保存串成一条可追踪的维护路径。后续改 edge 搜索、body 过滤、项目导出或桌面自动化时，可以先看文件职责再下手，减少重复定位成本。

可复用部分不只是目录树本身，还包括检查顺序：读复盘确认设计边界，读源码确认职责，读产物确认验证证据，再把可删除缓存和需要保留的样例分开写清楚。这个方法适合继续扩展 5 轴切片相关工具链。
